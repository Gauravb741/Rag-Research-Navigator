# Technical Approach

## 1. Why this problem

A researcher proposing a new RAG idea needs more than a list of semantically similar papers. They need to know:

- which prior methods address the same problem
- which datasets and metrics were used
- what limitations prior methods reported
- whether related papers are connected by citations or methodological lineage
- which research directions appear after those limitations

The project therefore focuses on **structured / graph-based RAG for multi-hop research synthesis** and implements the use case:

> Position a new RAG research idea in the prior-work landscape.

The system deliberately does not claim to prove novelty. It reports overlap within a bounded, inspectable corpus.

## 2. Corpus boundaries

The corpus contains 72 real research papers retrieved from the OpenAlex Works API using focused queries for graph RAG, knowledge-graph RAG, multi-hop retrieval, subgraph retrieval, document graphs, citation graphs, research question answering, and related benchmarks.

The full procedure is documented in `docs/CORPUS_SELECTION.md`. The selection is deterministic over cached API responses:

1. Search focused queries.
2. Run close-title searches for foundational baselines and directly relevant academic/citation-graph papers.
3. Reconstruct abstracts from OpenAlex inverted-index metadata.
4. Deduplicate normalized titles.
5. Score title/abstract focus terms.
6. Select the top 72 candidates.

The corpus includes papers from 2020–2026. It includes some domain applications when their method or evaluation is directly relevant to graph-RAG or multi-hop evidence; those papers are not treated as universally generalizable.

## 3. Knowledge model

The knowledge model is intentionally small and hand-authored. It is not generated by asking an LLM to build a graph, and it does not use an automatic knowledge-graph-construction library.

### Entities

| Entity | Purpose |
|---|---|
| Paper | Core scholarly unit and provenance anchor |
| Author | Supports author-paper connections |
| Method | Names a RAG, graph-RAG, retrieval, or reasoning method |
| ResearchProblem | Captures the problem a method addresses |
| Dataset | Captures the evaluated corpus or benchmark |
| Metric | Captures reported evaluation criteria |
| Architecture | Captures vector, graph, hierarchical, subgraph, or hybrid design |
| Limitation | Captures reported shortcomings or unresolved issues |
| ResearchDirection | Captures explicitly suggested or recurring next steps |
| Concept | Captures cross-paper structural ideas such as citation networks and evidence paths |

### Relationships

- `AUTHORED_BY`
- `CITES`
- `BUILDS_ON`
- `INTRODUCES_METHOD`
- `USES_METHOD`
- `ADDRESSES_PROBLEM`
- `EVALUATES_ON`
- `USES_METRIC`
- `IMPLEMENTS_ARCHITECTURE`
- `HAS_LIMITATION`
- `SUGGESTS_DIRECTION`
- `RELATES_TO_CONCEPT`

This is enough to support the approved use case without pretending to model all scholarly semantics.

## 4. Relationship construction

`src/modeling/ontology.py` contains a controlled vocabulary. Every term has:

- stable entity ID
- entity type
- human-readable name
- description
- aliases used for matching

`scripts/build_knowledge.py` applies the following transparent rules:

- title/abstract alias match → typed paper-to-entity relationship
- method alias in title → `INTRODUCES_METHOD`
- method alias only in abstract → `USES_METHOD`
- problem alias → `ADDRESSES_PROBLEM`
- dataset alias → `EVALUATES_ON`
- metric alias → `USES_METRIC`
- limitation alias → `HAS_LIMITATION`
- direction alias → `SUGGESTS_DIRECTION`
- architecture alias → `IMPLEMENTS_ARCHITECTURE`
- concept alias → `RELATES_TO_CONCEPT`
- OpenAlex referenced work present in the selected corpus → `CITES`
- later paper cites an earlier paper and has an explicit extension/improvement cue → `BUILDS_ON`

The mapping is conservative. It does not infer arbitrary relations from an LLM. Each edge contains a source paper, evidence text, source location, evidence type, and stable relationship ID.

## 5. Inspectable knowledge state

The central artifact is:

```text
data/knowledge/knowledge_state.json
```

It contains:

- metadata and schema version
- entity-type counts
- relationship-type counts
- all entities
- all relationships
- paper records with identifiers and source URLs

For convenience, the same state is split into:

- `data/knowledge/entities.json`
- `data/knowledge/relationships.json`
- `data/knowledge/build_summary.json`

A reviewer can inspect these files without starting the CLI.

## 6. New-input pipeline

The input is a free-text RAG research idea or short abstract. It is not added to the original corpus or knowledge state.

The reasoning flow is:

```text
new idea
  ↓
controlled-vocabulary seed matching
  ↓
reverse graph lookup from matched problems/methods/concepts
  ↓
candidate papers
  ↓
citation and build-on expansion
  ↓
paper-to-limitation/direction/problem paths
  ↓
evidence attachment
  ↓
structured positioning report
```

The system accepts terminology only when it can match a controlled alias. This reduces unsupported claims and makes false positives visible in the uncertainty notes.

## 7. Reasoning engine

`src/reasoning/engine.py` implements the graph reasoner.

### Candidate scoring

1. Match input aliases against controlled entities.
2. Traverse reverse paper-to-entity edges to find candidate papers.
3. Give higher graph weight to method and problem matches.
4. Expand one hop through in-corpus `CITES` and `BUILDS_ON` edges.
5. Use lexical similarity only as a tie-breaker/candidate locator.
6. Rank papers by graph score, lexical tie-break, citation count, and year.

### Path generation

For the top candidates, the engine emits paths such as:

```text
matched problem
  → paper
  → limitation
```

or:

```text
matched concept
  → paper A
  → CITES
  → paper B
  → research direction
```

Every path carries relationship IDs that can be looked up in `knowledge_state.json`.

### Output

The structured report contains:

- `input_summary`
- `matched_concepts`
- `related_methods`
- `related_architectures`
- `related_problems`
- `related_datasets`
- `related_papers`
- `foundational_connections`
- `multi_hop_evidence_paths`
- `known_limitations`
- `research_directions`
- `recommended_reading_order`
- `evidence`
- `flat_retrieval_baseline`
- `uncertainty_notes`
- `reasoning_summary`

## 8. Baseline

`src/retrieval/lexical.py` provides a dependency-free TF-IDF-like cosine retrieval baseline over paper title and abstract.

The baseline is intentionally not used as the final reasoning layer. It is used to show the difference between:

- flat paper retrieval
- graph-connected entity and relation reasoning with evidence paths

The evaluation reports entity-coverage diagnostics for both approaches and separately reports graph paths and evidence completeness.

## 9. Evaluation

`data/evaluation/test_cases.json` contains four manually specified ideas not present as papers in the corpus. Each case includes expected useful entity connections.

`scripts/evaluate.py` reports:

- expected entity coverage for the graph system
- expected entity coverage for the flat baseline
- graph-path count
- whether graph reasoning was used
- evidence count
- evidence grounding completeness
- top returned papers

These are small project diagnostics, not a universal benchmark. No scores are invented; the numbers in `data/evaluation/evaluation_results.json` are generated by the evaluation script.

## 10. Design tradeoffs

### JSON instead of a graph database

JSON keeps the knowledge state inspectable, portable, and easy to review. The corpus is only 72 papers, so a graph database would add deployment complexity without being necessary for the demonstration.

### Controlled rules instead of automatic KG extraction

The assignment requires an inspectable knowledge state and does not want an automatic knowledge graph-construction tool. A hand-authored vocabulary plus deterministic evidence-bearing rules makes the transformation auditable and reproducible.

### Lexical seed matching instead of an LLM parser

A local deterministic matcher avoids API keys and makes behavior reproducible. Its limitation is explicit: terminology outside the ontology can be missed.

### CLI plus dependency-free web atlas

The CLI remains the reproducible automation surface, while the local web atlas makes the structured state inspectable for a researcher. The atlas is served from the standard-library Python server, consumes a filtered `/api/graph` projection of the serialized knowledge state, and calls the existing reasoner through `/api/reason`; it does not introduce a second reasoning implementation or a frontend dependency stack. This preserves scripted evaluation while making graph paths, relationship evidence, paper details, and publication-time context visible in one workflow.

## 11. What was intentionally not built

- No general-purpose chatbot
- No decorative dashboard
- No vector database as the only knowledge representation
- No automatic LLM-generated knowledge graph
- No absolute novelty detector
- No claim that a paper is universally foundational
- No hidden external API call during reasoning

## 12. Web interface and security boundary

The web UI is a dependency-free same-origin application served by `src/interface/web.py` and started with `scripts/serve.py`.

The browser communicates only with:

- `GET /` for the self-contained UI
- `GET /api/health` for non-sensitive graph counts
- `GET /api/graph` for the filtered, serialized entity/relationship projection used by the atlas
- `POST /api/reason` for a bounded research idea

The backend loads one fixed local knowledge-state path. It does not expose a general static-file server, execute user input, accept uploads, invoke a shell, or use a database.

User ideas and external research metadata are rendered with `textContent` and DOM node creation. The frontend does not use unsafe HTML injection, `eval`, local storage, external scripts, or external fonts. Paper links are restricted to HTTP(S) and receive `noopener noreferrer`.

The API validates JSON shape, content type, body size, input length, UTF-8, and control characters. User ideas are not logged. Responses include no stack traces or filesystem details. The server sends a restrictive content security policy and browser security headers and does not enable CORS.

The full review is documented in `docs/SECURITY_REVIEW.md`. The demo intentionally binds to `0.0.0.0` for sandbox preview compatibility; an internet-facing deployment would require HTTPS, authentication, rate limiting, a production server, and a nonce/hash-based CSP instead of the preview-compatible inline policy.

## 13. Limitations and future work

The current system has a small ontology, lexical mapping, bounded citation edges, and a small manually specified evaluation set. It may miss synonymous terminology and cannot guarantee that every semantic relationship is captured.

The next research improvements would be expert relation annotation, temporal limitation-to-direction reasoning, richer citation metadata, stronger dense/hybrid retrieval baselines, and richer temporal/path analysis in the atlas.
